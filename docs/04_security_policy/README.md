# Регламент обеспечения кибербезопасности системы антивирусной защиты

**Версия документа:** 1.0
**Область действия:** аттестованный сегмент сети `10.20.30.0/24`, Сервер
администрирования KSC и все защищаемые узлы

---

## 1. Общие положения

### 1.1. Назначение

Регламент устанавливает порядок обеспечения защищённости системы
антивирусной защиты, распределение обязанностей и порядок действий при
инцидентах.

### 1.2. Основные принципы

| Принцип | Реализация |
|---|---|
| Единая точка управления | Управление Сервером возможно только с АРМ администратора `10.20.30.15` |
| Минимум полномочий | Разделение ролей: администратор, оператор, аудитор; служебным учётным записям запрещён интерактивный вход |
| Изолированность контура | Обращения к внешним сетям отсутствуют; участие в облачных службах производителя отключено |
| Контролируемость состава сети | Статическая адресация, ручной перечень узлов, ежемесячный опрос диапазона адресов |
| Полнота регистрации | Срок хранения событий 365 суток, передача в систему мониторинга |
| Обратимость изменений | Каждый сценарий изменения состояния узла сохраняет данные для отката |

### 1.3. Распределение обязанностей

| Роль | Обязанности |
|---|---|
| Администратор системы защиты | Развёртывание, настройка, эксплуатация, устранение неисправностей, реагирование на инциденты |
| Администратор безопасности | Согласование изменений, контроль соблюдения регламента, разбор нарушений, проверка журналов действий администраторов |
| Оператор | Наблюдение за состоянием защиты, первичный разбор событий, запуск задач проверки |
| Аудитор | Контроль соответствия фактического состояния установленным требованиям |
| Пользователь | Соблюдение руководства пользователя, сообщение о выявленных признаках инцидентов |

Совмещение ролей администратора системы защиты и администратора
безопасности одним лицом не допускается: контроль действий администратора
должен выполняться независимо.

## 2. Управление доступом

### 2.1. Доступ к управлению системой

| Требование | Значение |
|---|---|
| Точка доступа | Только АРМ администратора `10.20.30.15` |
| Порты управления | 13291, 13299, 8080, 3389, 5985 — доступны только с указанного адреса и с адресов смежных средств защиты по согласованному перечню |
| Способ аутентификации | Доменная учётная запись, членство в группе `KSC-Admins`; локальные учётные записи Сервера не применяются |
| Многофакторная аутентификация | Применяется при наличии технической возможности |
| Хранение паролей в браузере и файлах | Не допускается |

Изменение перечня адресов, которым разрешено управление, выполняется
только через параметр `SecurityToolsHosts` в `common/config.ps1` с
последующим применением сценария правил межсетевого экрана. Каждое
изменение согласуется с администратором безопасности и фиксируется.

### 2.2. Требования к паролям

| Учётная запись | Длина | Срок действия | Хранение |
|---|---|---|---|
| Администратор системы защиты | не менее 14 символов | 90 суток | Хранилище паролей организации |
| `svc_ksc` (служба Сервера) | не менее 20 символов | не ограничен, смена при компрометации и при смене администратора | Хранилище паролей организации |
| `svc_ksc_deploy` | не менее 20 символов | не ограничен | То же |
| `kscadmin` (СУБД) | не менее 20 символов | не ограничен | То же |
| Пароль защиты Агента от удаления | не менее 12 символов | по решению администратора | То же |

Пароли не хранятся в файлах репозитория. Сценарии запрашивают их при
выполнении и не записывают в журналы.

### 2.3. Пересмотр прав доступа

| Действие | Периодичность |
|---|---|
| Проверка состава групп `KSC-Admins`, `KSC-Operators`, `KSC-Auditors` | Ежеквартально |
| Проверка состава локальных администраторов Сервера и АРМ | Ежеквартально |
| Отзыв прав при переводе или увольнении сотрудника | В день издания приказа |

## 3. Требования к защищённости узлов

### 3.1. Обязательные меры

Узлы системы относятся к системам служебного пользования: применяется
расширенный (строгий) профиль защищённости. Полный состав мер — в
приложении к руководству администратора
[«Расширенный профиль защищённости узлов»](../02_admin_guide/hardening_profile.md).

| Мера | Сервер KSC | АРМ администратора | Узел Windows | Узел Debian |
|---|---|---|---|---|
| Агент администрирования | — | обязателен | обязателен | обязателен |
| Средство защиты узла | обязательно | обязательно | обязательно | обязательно |
| Запрет входящих подключений по умолчанию | да | да | да | да |
| Отключение устаревших протоколов (SMBv1, LLMNR, NetBIOS) | да | да | да | не применимо |
| Отключение SSL 2.0/3.0, TLS 1.0/1.1 | да | да | да | да |
| Запрет LM и NTLMv1, только NTLMv2 | да | да | да | не применимо |
| Защита учётных данных (LSA Protection, Credential Guard) | да | да | да | не применимо |
| Кеширование доменных входов | не более 2 | запрещено | не более 2 | не применимо |
| Журналирование PowerShell и ограничение запуска сценариев | да (`RemoteSigned`) | да (`AllSigned`) | да (`AllSigned`, ограниченный язык) | не применимо |
| Съёмные носители | запрет записи | запрещены | запрет записи | запрет загрузки `usb-storage` |
| Управление запуском программ (AppLocker) | режим наблюдения | режим наблюдения | режим наблюдения | не применимо |
| Расширенная регистрация событий | да | да | да | да (auditd) |
| Удалённый доступ | только с АРМ | только по согласованию | отключён | SSH по ключам только с АРМ |
| Автоматическое обновление из внешних источников | отключено | отключено | отключено | отключено |

Применение мер выполняется сценариями каталога `hosts/*/hardening`.
Каждый сценарий поддерживает режим проверки без внесения изменений.

Переход на базовый профиль (`-Level Baseline`, `--level baseline`)
допускается только как временная мера при нарушении работы прикладного
ПО, подлежит регистрации как исключение (раздел 6.3) с указанием срока
возврата к расширенному профилю.

### 3.2. Особые условия для контроллеров домена

Меры защищённости на контроллерах домена применяются только в режиме
проверки (`-Mode Audit`). Изменение параметров аутентификации домена
(подпись LDAP, ограничение NTLM, типы шифрования Kerberos) выполняется
отдельно, поэтапно, с предварительной проверкой совместимости всех
клиентов, включая узлы Debian и смежные средства защиты. Ошибка приводит
к отказу аутентификации во всей сети.

Установка Агента администрирования на контроллер домена выполняется в
согласованное окно после проверки на резервном узле; групповая политика
установки к подразделению контроллеров домена не привязывается.

## 4. Регистрация событий и хранение сведений

### 4.1. Сроки хранения

| Категория | Срок | Место |
|---|---|---|
| События узлов и Сервера | 365 суток | База данных MariaDB |
| Отчёты | 365 суток | База данных MariaDB |
| Журнал действий администраторов | 365 суток | База данных MariaDB |
| Резервные копии данных Сервера | 30 суток (30 копий) | Том `E:` и сетевой ресурс |
| Журнал безопасности Windows | до заполнения объёма 1 ГБ, с передачей в систему мониторинга | Узел |
| Материалы разбирательства по инциденту | 3 года | Хранилище документов |

Уменьшение срока хранения событий не допускается. При недостаточности
дискового пространства увеличивается объём тома `D:`, а не сокращается срок.

### 4.2. Контроль соблюдения срока

Хранение ограничивается одновременно сроком и предельным числом событий:
превышение любого из ограничений приводит к удалению наиболее старых
событий. Поэтому ежемесячно проверяется, что фактический годовой объём
событий не превышает установленный предел (исходно 20 000 000). При
приближении к пределу он увеличивается либо сокращается перечень
регистрируемых малозначимых событий.

### 4.3. Передача в смежные средства защиты

События критической и предупреждающей важности передаются в систему
мониторинга по протоколу syslog в формате CEF. Перечень адресов получателей
и порт указываются в `common/config.ps1` и отражаются в таблице
информационных потоков.

## 5. Порядок реагирования на инциденты

### 5.1. Классификация

| Уровень | Признаки | Срок реакции | Срок устранения |
|---|---|---|---|
| Критический | Вредоносная программа не устранена; признаки шифрования файлов; отключение средства защиты на узле; несанкционированный доступ к Серверу | Незамедлительно | 4 часа |
| Высокий | Массовое обнаружение угроз (более 5 узлов за сутки); узел без Агента, выявленный опросом; отказ Сервера администрирования | 1 час | 8 часов |
| Средний | Единичное обнаружение с успешным устранением; базы устарели более чем на 3 суток; невыполнение резервного копирования | 4 часа | 1 сутки |
| Низкий | Отставание баз до 3 суток; невыполнение задачи проверки по расписанию | 1 рабочий день | 3 рабочих дня |

### 5.2. Порядок действий

**Этап 1. Выявление и регистрация.** Источники: уведомления консоли,
сообщение пользователя, результат ежедневного контроля. Инцидент
регистрируется в журнале с указанием времени выявления, узла, признаков.

**Этап 2. Локализация.** При критическом уровне:

1. Изолировать узел от сети — отсоединением кабеля либо блокировкой порта
   коммутатора. **Узел не выключать:** выключение уничтожает сведения в
   оперативной памяти, необходимые для разбирательства.
2. Сохранить снимок состояния виртуальной машины, если узел виртуальный.
3. Определить, затронуты ли иные узлы: поиск того же признака по всем
   узлам средствами консоли.

**Этап 3. Устранение.** Выполняется полная проверка узла, устранение
обнаруженных объектов, при необходимости — восстановление узла из
эталонного образа. Восстановление предпочтительнее лечения, если объект
обладал правами системы.

**Этап 4. Восстановление.** Узел возвращается в сеть после подтверждения
отсутствия угроз: полная проверка без обнаружений, актуальные базы,
работающий Агент.

**Этап 5. Разбирательство.** В течение 3 рабочих дней определяются: путь
проникновения, перечень затронутых узлов, достаточность принятых мер,
необходимые изменения политик. Результат оформляется письменно.

### 5.3. Обязательное уведомление

| Событие | Кого уведомить | Срок |
|---|---|---|
| Инцидент критического уровня | Администратор безопасности, руководитель подразделения | Незамедлительно |
| Признаки программы-вымогателя | Администратор безопасности, руководитель организации | Незамедлительно |
| Несанкционированный доступ к Серверу администрирования | Администратор безопасности | Незамедлительно |
| Выявление узла, не учтённого в перечне | Администратор безопасности | 1 рабочий день |

## 6. Управление изменениями

### 6.1. Изменения, требующие согласования

| Изменение | Согласование | Обоснование |
|---|---|---|
| Изменение перечня адресов, которым разрешено управление | Администратор безопасности | Расширяется поверхность доступа к системе управления |
| Изменение сроков хранения событий | Администратор безопасности | Влияет на возможность разбирательства |
| Ослабление политики защиты, добавление исключений проверки | Администратор безопасности | Создаёт участки, не контролируемые средством защиты |
| Установка Агента на контроллер домена | Администратор безопасности | Риск отказа аутентификации в сети |
| Применение средств управления конфигурацией (Ansible) | Администратор безопасности | Появляется новый канал управления узлами, не учтённый в схеме потоков |
| Подключение узла к внешней сети | Не допускается | Нарушение условий аттестации |

### 6.2. Порядок внесения изменений

1. Изменение параметров вносится в `common/config.ps1` (для Linux — в
   `hosts/linux-debian/common.sh`), а не в отдельные сценарии: параметры
   должны иметь единый источник.
2. Изменение проверяется в режиме предварительного просмотра
   (`-WhatIf` либо `--check`).
3. Изменение применяется в согласованное окно.
4. Результат проверяется приёмочным сценарием.
5. Запись вносится в журнал изменений с указанием даты, исполнителя,
   основания и способа отката.

### 6.3. Исключения проверки

Каждое исключение из области проверки средства защиты (каталог, процесс,
узел) должно быть:

- обосновано письменно;
- согласовано с администратором безопасности;
- внесено в перечень исключений с указанием срока действия;
- пересмотрено не реже одного раза в год.

Исключения, созданные при развёртывании (каталоги базы данных и Сервера
администрирования), обусловлены требованиями производителя и пересмотру
не подлежат, но подлежат учёту.

## 8. Ответственность

Нарушение требований настоящего регламента влечёт ответственность в
установленном порядке. К нарушениям относятся, в частности:

- подключение к системе управления с узла, не входящего в перечень
  разрешённых;
- отключение или удаление средства защиты на узле;
- внесение изменений в параметры защиты без согласования;
- сокрытие факта инцидента;
- передача параметров доступа другим лицам;
- вынос сведений системы за пределы аттестованного контура.
