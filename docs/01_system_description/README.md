# Общее описание системы централизованного управления антивирусной защитой

**Условное обозначение:** САЗ КSC
**Версия документа:** 1.0
**Дата:** 2026
**Статус:** проект, подлежит согласованию

> Документ описывает проектное состояние системы. Значения, выделенные как
> `<уточняется>`, заполняются перед согласованием: реальное имя домена,
> адреса смежных средств защиты информации, версии программного обеспечения.

---

## 1. Назначение и цели создания системы

### 1.1. Назначение

Система предназначена для централизованного управления средствами
антивирусной защиты автоматизированной системы, размещённой в аттестованном
сегменте локальной вычислительной сети `10.20.30.0/24`.

Система обеспечивает:

- централизованное управление параметрами защиты всех узлов сети;
- контроль состояния защиты и выявление незащищённых узлов;
- централизованное обновление антивирусных баз без обращения к внешним сетям;
- регистрацию и хранение событий безопасности в течение одного года;
- передачу событий в смежные средства защиты информации;
- инвентаризацию программного и аппаратного обеспечения узлов.

### 1.2. Цели создания

| Цель | Показатель достижения |
|---|---|
| Полный охват узлов сети средствами антивирусной защиты | Доля узлов с установленным Агентом администрирования — 100 % от узлов, для которых установка предусмотрена |
| Централизация управления | Все параметры защиты задаются политиками с единого Сервера; локальное изменение параметров пользователем исключено |
| Контролируемость доступа к управлению | Управление возможно только с АРМ администратора; доступ с иных узлов заблокирован |
| Сохранность сведений о событиях | Срок хранения событий и отчётов — 365 суток |
| Работоспособность в изолированном контуре | Отсутствие обращений системы к внешним сетям |

### 1.3. Ограничения

Система **не решает** следующие задачи, которые относятся к смежным
средствам защиты:

- обнаружение вторжений на сетевом уровне;
- контроль доступа в сеть;
- анализ защищённости и управление уязвимостями инфраструктуры за пределами
  контролируемых узлов;
- централизованный сбор и корреляция событий всех источников (эта задача
  решается системой мониторинга событий, куда САЗ передаёт свои события).

## 2. Условия функционирования

### 2.1. Характеристика сегмента сети

| Характеристика | Значение |
|---|---|
| Адресное пространство | `10.20.30.0/24` |

| Фактическое число контролируемых узлов | около 50 |
| Перспективное расширение | до 50 дополнительных узлов пользователей и администраторов (в текущий объём не входит) |

### 2.3. Характеристика Сервера администрирования

| Ресурс | Выделено | Обоснование достаточности |
|---|---|---|
| Процессор | 4 ядра | Достаточно для 254 узлов; при расширении до расчётного запаса в 1000 узлов потребуется 6–8 ядер |
| Оперативная память | 16 ГБ | Из них 6 ГБ выделяется буферному пулу СУБД, остаток — Серверу администрирования и операционной системе |
| Дисковое пространство | 400 ГБ | Разделяется на три тома (см. ниже) |

Разделение дискового пространства обязательно: при едином томе рост базы
данных или хранилища обновлений приводит к исчерпанию системного тома и
отказу операционной системы.

| Том | Объём | Содержимое |
|---|---|---|
| `C:` | 120 ГБ | Операционная система, Сервер администрирования |
| `D:` | 150 ГБ | Файлы базы данных MariaDB |
| `E:` | 130 ГБ | Общий ресурс `KLSHARE`, хранилище обновлений, резервные копии |

Оценка объёма базы данных: при 254 узлах и сроке хранения событий 365 суток
ожидаемый размер составляет 40–80 ГБ. Резерв тома `D:` предусмотрен для
временных файлов СУБД и роста при увеличении числа событий.

## 3. Структура системы

### 3.1. Функциональные компоненты

| Компонент | Размещение | Функция |
|---|---|---|
| Сервер администрирования | `ksc` | Хранение политик и параметров, управление задачами, приём событий от Агентов |
| СУБД MariaDB | `ksc`, только локальный интерфейс | Хранение параметров, сведений об узлах и событий |
| Web Console | `ksc`, порт 8080 | Интерфейс управления через браузер |
| Консоль администрирования MMC | АРМ администратора | Интерфейс управления, дополняющий Web Console |
| Общий ресурс `KLSHARE` | `ksc`, том `E:` | Хранение дистрибутивов и пакетов установки |
| Веб-сервер | `ksc`, порты 8060/8061 | Раздача автономных пакетов установки |
| Агент администрирования | все защищаемые узлы | Связь узла с Сервером, применение политик, передача событий |
| Средство защиты узла | все защищаемые узлы | Kaspersky Endpoint Security для Windows / для Linux |

Совмещение Сервера администрирования и СУБД на одном узле допустимо при
числе узлов до нескольких тысяч и выбрано осознанно: разнесение потребовало бы
второго узла и передачи данных СУБД по сети, что расширило бы перечень
информационных потоков без выигрыша в производительности при указанном
масштабе.

### 3.2. Схемы

Схемы приведены в каталоге `docs/05_diagrams`:

- `structural.drawio` — структурная схема: узлы, их роли и физические связи;

## 4. Организация управления доступом

### 4.1. Принцип единой точки управления

Управление системой возможно **только с АРМ администратора** `10.20.30.15`.
Правила межсетевого экрана Сервера администрирования разрешают подключение
к портам управления (13291, 13299, 8080, 3389, 5985) исключительно с этого
адреса и с адресов смежных средств защиты информации, указанных в перечне.

Служебные порты, необходимые для работы Агентов (13000/TCP, 13000/UDP,
14000/TCP, 8060/8061/TCP), разрешены для всего сегмента: без этого узлы не
смогут передавать сведения о своём состоянии. Разделение «управление — по
перечню адресов, служебное взаимодействие — по сегменту» является основой
модели доступа.

### 4.2. Роли

| Роль | Группа безопасности | Полномочия |
|---|---|---|
| Главный администратор | `<домен>\KSC-Admins` | Полное управление: политики, задачи, учётные записи, параметры Сервера |
| Оператор | `<домен>\KSC-Operators` | Просмотр состояния, запуск задач проверки, работа с событиями; изменение политик недоступно |
| Аудитор | `<домен>\KSC-Auditors` | Только просмотр: события, отчёты, журнал действий администраторов |

### 4.3. Служебные учётные записи

| Учётная запись | Назначение | Ограничения |
|---|---|---|
| `<домен>\svc_ksc` | Работа службы Сервера администрирования | Запрет интерактивного входа, запрет делегирования, срок действия пароля не ограничен |
| `<домен>\svc_ksc_deploy` | Удалённая установка Агентов | Права локального администратора на защищаемых узлах, запрет интерактивного входа |

## 5. Порядок обработки событий

### 5.1. Хранение

| Категория сведений | Место хранения | Срок |
|---|---|---|
| События узлов и Сервера | База данных MariaDB | 365 суток |
| Отчёты | База данных MariaDB | 365 суток |
| Журнал действий администраторов | База данных MariaDB | 365 суток |
| Резервные копии | Том `E:` и сетевой ресурс | 30 копий (ежедневно) |
| Журналы операционной системы Сервера | Журнал событий Windows | до заполнения журнала объёмом 1 ГБ |

Срок хранения 365 суток установлен требованием к системе. Соблюдение срока
контролируется двумя параметрами одновременно: сроком хранения и предельным
числом событий — при достижении любого из них наиболее старые события
удаляются. Поэтому предельное число событий должно быть заведомо выше
годового объёма; исходное значение — 20 000 000, подлежит уточнению по
фактическому темпу поступления событий за первый месяц эксплуатации.

### 5.2. Передача в смежные средства защиты

События передаются в систему мониторинга событий по протоколу syslog в
формате CEF. Перечень передаваемых событий ограничивается событиями
критической и предупреждающей важности, чтобы не создавать избыточный поток.

## 6. Обеспечение непрерывности

| Мера | Реализация | Периодичность |
|---|---|---|
| Резервное копирование данных Сервера | `klbackup.exe`, том `E:`, вынос на сетевой ресурс | Ежедневно |
| Сохранение сертификата Сервера | Отдельное хранение вне узла | При каждом изменении |
| Проверка восстановления | Восстановление на резервный узел | Не реже одного раза в год |
| Обслуживание базы данных | Задача обслуживания Сервера | Еженедельно |

Сертификат Сервера администрирования сохраняется отдельно и является
критичным элементом: при его утрате восстановление Сервера не восстанавливает
доверие Агентов, и подключение каждого узла придётся выполнять заново вручную.
